Overview

Fixing data, auditing a database or answering a support ticket often needs one SQL statement. Without this module that means opening psql, sharing server credentials or asking a hosting provider. yDoD PostgreSQL Query Execute adds a SQL console under Settings → Technical → SQL Console: an administrator types a statement, clicks Execute and sees the result as a table with column names, row count and execution time. SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER and DROP are all supported.

Every saved query carries a Note explaining what it does, why it exists and what it could break, so the next person understands it before running it. Write statements require an explicit Allow data modification tick and run inside a savepoint, PostgreSQL errors are shown in the form instead of breaking the session, every run is logged in History, and any result table prints to PDF.

Built for Odoo system administrators, technical consultants, support engineers and developers who need to inspect or fix data directly in PostgreSQL from the Odoo backend without shell or psql access.

Features in Detail

SQL console form

Open Settings → Technical → SQL Console → Queries and create a query: a Name, the statement in the SQL tab, Max rows (default 200, configurable through the system parameter ydod_postgresql_query_execute.default_max_rows) and the PDF Orientation. The Statement Type field is computed automatically: Read for SELECT, EXPLAIN, SHOW, TABLE, VALUES and read-only WITH queries, Write for everything else.

  • Click Execute: the form is saved, the statement runs and the status bar switches to Success or Error.
  • The Result tab shows column headers, the rows (capped at Max rows with a “Showing X of Y rows” notice), rows returned or affected, duration, run date and user.
  • INSERT, UPDATE, DELETE, CREATE, ALTER and DROP report the number of affected rows; several statements separated by semicolons run as one batch and the result of the last one is shown.

Documentation note

The Note tab is a rich-text field placed next to the SQL so it is read before execution. Use it to record what the query does, why it was written and what it could break. The note is printed on the PDF and copied when a past run is loaded into a new query, so the context travels with the statement.

Example library

Installation ships eight documented queries flagged as Example (filter Examples in the list). They are regular records: edit them, run them or use Action → Duplicate to start your own version. Edits survive module upgrades.

  • Installed modules and versions, Largest tables, Overdue cron jobs, Users and last login.
  • Duplicate partners by email, Duplicate partners by VAT.
  • Unposted journal entries (needs Invoicing) and Stock quants below zero (needs Inventory); on a database without these apps the error message demonstrates failure reporting.

Execution history

Every click on Execute, successful or not, creates a line under SQL Console → History with the query name, the SQL exactly as executed, user, run date, duration, rows, statement type, status and error message. History lines are immutable: even administrators have no update right, and they stay when the query is deleted.

  • The History smart button on a query opens its own runs; the History tab shows them inline.
  • Load into editor copies a past statement and the original note into a new query, with Allow data modification unticked.
  • Filters My Runs, Errors, Write Statements, Today and Last 7 Days; group by User, Status, Query or Run Date.

PDF export of results

After a run, Print PDF renders the last result with the company layout: query name, run date, user, duration, row count, the note, the SQL and the result table. The paper orientation follows the Orientation field of the query: A4 portrait uses the standard Odoo paper format, A4 landscape uses a dedicated format with narrow margins for wide tables. The file is named “SQL - query name”.

Safety guards

  • Write statements are refused with a clear message until Allow data modification is ticked; nothing is executed or logged in that case.
  • Statements run inside a savepoint: read statements are always rolled back (a SELECT calling a function that writes changes nothing), write statements are released into the current transaction.
  • A PostgreSQL error appears in a red alert in the Result tab and the transaction stays valid, so you fix the SQL and run again.
  • BEGIN, COMMIT, ROLLBACK, SAVEPOINT and similar transaction control statements cannot be saved; Max rows is limited to 1–5000.

Access control

Both models and all menus are restricted to the Administration / Settings group (base.group_system). Statements run with the connected administrator's own database cursor, never with elevated rights. Internal users get an access error if they try to open the models by URL.

How to Use

  1. Install the module from Apps. It only needs base and web, which every Odoo 17.0 database already has.
  2. Grant access: the user must belong to Administration → Settings. Activate developer mode to see the Technical menu.
  3. Optional setting: in Settings → Technical → System Parameters, create ydod_postgresql_query_execute.default_max_rows to change the default Max rows (200) for new queries.
  4. Open Settings → Technical → SQL Console → Queries; the Examples filter shows the shipped library.
  5. Create or duplicate a query: fill Name, the SQL tab and the Note tab; set Max rows and Orientation.
  6. Tick Allow data modification only when the statement must write data, then click Execute.
  7. Read the Result tab: the table, rows, duration and, if any, the red PostgreSQL error.
  8. Print PDF to download the result table, or open History to audit runs and use Load into editor.

Frequently Asked Questions

Which users can see the SQL Console?

Only members of the Administration / Settings group. The menus sit under Settings → Technical, so developer mode must be active. No other group gets access rights, so the console cannot be opened by regular employees.

Can a wrong statement break my database?

Read statements are always rolled back and a failed statement is rolled back to its savepoint, so typos are harmless. Write statements with Allow data modification ticked do change data, exactly as they would in psql, and are committed with the request. Read the note, test on a staging database and keep backups for destructive statements.

Does it work in multi-company databases?

Yes. Queries and history have no company field because the PostgreSQL database is shared by all companies by design; your SQL decides which company's rows it touches.

Are large results a problem?

Only Max rows (1 to 5000, default 200) are kept and displayed; the total row count still comes from PostgreSQL. Add LIMIT or raise Max rows on the query when you need more.

What happens to history lines when a query is deleted?

They are kept with an empty Query reference, so the audit trail stays complete. History lines cannot be edited by anyone; administrators can delete them.

What happens on uninstall?

The queries, the example library, the history and the two report actions are removed. Tables or data changed by your own statements are of course untouched. No external service is involved.
